# 2026-05-09 — MOC Creation Skill (spec 013, F-43)

## Summary

Delivered `/moc-propose` — a standalone skill that discovers under-organised topic
clusters in the vault and proposes a new MOC (Map of Content) for user review.
Six input modes. Additive extension to the existing 2-pass pipeline. Requires
Hashi 0.2.0+ for the destination-collision guard (shipped 2026-05-07).
Production launch pending live-vault validation (T6.2) and the Hashi version
launch gate (T6.4).

## Why

After the inbox fan-out pipeline (XDD 004) and daily-note workflow (XDD 005) were
complete, the vault had no proactive MOC-creation surface. Notes were accumulating
without MOC parents, and the only MOC-creation trigger (`needs_new_moc` in Pass 1
batch clusters) fired only mid-inbox-run — not on demand, not for a topic the user
had in mind before opening `/inbox`. F-43 adds a first-class `/moc-propose <topic>`
command that operates independently of the inbox and feeds its output back into the
existing `create_moc` + `add_relationship` action schema.

## Scope shipped

### Six input modes

| Mode | Trigger |
|------|---------|
| 1 | `topic` — free-text keyword, broad vault scan |
| 2 | `folder` — all atomic notes inside a specified vault path |
| 3 | `classification` — a Dewey sub-code (miyo profile) or topic prefix (LYT) |
| 4 | `tag` — atomic notes carrying a given tag |
| 5 | `placeholder` — unresolved wikilink that references a non-existent MOC file |
| 6 | `whole-vault` — full atlas scan across all concept paths |

### New components

- `tomo/.claude/agents/moc-architect.md` — orchestrates the 2-step proposal
  workflow: discovery → proposal-doc write
- `scripts/moc-discovery.py` — reads the discovery cache and vault-config to
  produce a JSON cluster manifest; does not call Kado directly; reads the
  full atomic-notes index baked into the cache by `/explore-vault`
- Proposal doc written to the inbox at `+/moc-proposals/<topic-slug>.md` —
  the same human-review surface as Pass-1 suggestions

### Squelch lifecycle (Phase 5)

`moc-discovery.py` reads `config/discovery-cache.yaml` at startup and decrements
the cache's `moc_sidecar_count` before emitting clusters. This suppresses
duplicate proposals when the user runs `/moc-propose` for a topic that already has
a pending proposal in the inbox. A `.tmp` sidecar is never written on rollback.
Test coverage: `tests/test_F43_T5_1_squelch.py`, `tests/test_F43_T5_2_existing_moc.py`.

### Cross-repo: Hashi destination-collision guard

F-43 SDD ADR-3 records a new Hashi-side requirement: `create_moc` must fail with
`applied: false` + `error_msg: "destination already exists: <path>"` when the
target file already exists, and must cascade that failure to dependent
`add_relationship` / `link_to_moc` actions. Hashi 0.2.0 shipped the guard on
2026-05-07. The cross-repo handoff is archived at
`_archive/outbox/2026-05/2026-05-07_tomo-to-hashi_create-moc-collision-guard.md`.

## Phase 6 surprise — unwired `moc-discovery.py main()`

During Phase 6 acceptance testing (T6.0), the `moc-discovery.py` module was found
to have no `main()` entry point despite Phase 2 being marked done. The orchestration
wire from `moc-architect.md` had no script to call. T6.0 backfilled the `main()`
function and re-connected the agent → script call chain.

**Lesson for future spec work:** Phase 3 "Live producer smoke" must be a real
done-criterion — a script that is callable end-to-end via CLI — not just "file
written and tests pass." The smoke-test task must verify the actual execution path,
not just unit-level assertions.
