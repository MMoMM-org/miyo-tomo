| 2026-09-03 | Spec scaffolded from issue [#157](https://github.com/MMoMM-org/miyo-tomo/issues/157) | Found while validating spec 032 on live data. `_resolve_up_state` (`moc-tree-builder.py:280`) returns `broken` for exactly one condition — *the `up::` target is not the stem of an in-scope MOC*. Three unrelated vault states collapse onto that one label, and `_check_broken_up` offers all three the same remedy: *"repoint it to a MOC you enter below, or leave empty to remove"*. |
| 2026-09-03 | The remedy is correct for **one** of the three causes | Target genuinely missing → remove/repoint is right. Target exists in scope but carries no MOC tag → **the link works**; removing it deletes a real parent. Target exists outside `scope_paths` → **the scanner is blind, not the vault**. A user working the list in good faith flattens deliberate hierarchy. |
| 2026-09-03 | Population measured on the live cache, not estimated | 2026-09-03 rebuild: 359 entries, 42 `broken_up`. **20** targets are present in the cache as `kind: note` (cause 2). **22** are absent from it (cause 1 or 3). Of those 22, seven name one target by bare stem while an eighth records the same target as a **full path under a folder outside `scope_paths`** — so cause 3 is confirmed, not hypothetical. At most a handful of the 42 are genuinely dangling. |
| 2026-09-03 | **The split costs nothing** — no new Kado calls, no new scan | `_resolve_up_state` is handed `moc_stem_set`, derived from `scan_result.moc_paths`. The same `ScanResult` already carries `in_scope_note_paths`, and the cache already stores every in-scope note with `kind: note` (measured: 64 MOCs + 295 notes). Distinguishing *valid* / *not-a-moc* / *unresolved* is a three-way test at the exact site of today's two-way test, over data already in hand. Contrast with spec 032, where the equivalent question also turned out to be free — same lesson twice. |
| 2026-09-03 | `unresolved` will **not** be split further into *missing* vs *out-of-scope* | The cache knows only its own scope; deciding whether an absent target exists elsewhere in the vault needs I/O this check does not have and must not acquire (`broken_up` is cache-only by construction — `_check_broken_up` takes no `graph_audit_fn`/`list_dir_fn`). The report will therefore say *"not found in the audited area"* rather than claim the note is gone. Honest under-claiming beats a wrong certainty. |
| 2026-09-03 | **`not-a-moc` becomes advisory with an inverted suggestion** (user decision) | Chosen over *"stop reporting it"* and *"report without a fix"*. The finding stops being an integrity defect and becomes an advisory naming the real gap: **the parent note carries no MOC tag**. The suggestion is the inverse of today's — *tag the target*, not *delete the link*. One tag often resolves several findings at once (measured: seven travel notes point at three parent notes). No Apply checkbox, so nothing destructive can be approved by accident. |
| 2026-09-03 | Scope boundary against spec 032, stated so it cannot drift | 032 decides **where** a broken-parent fix is written (`edit_frontmatter` vs a body edit) and is untouched by this spec. 033 decides **whether** a fix should be offered at all, and what it should say. The two meet only at the finding's `detail`, which gains one field. |
| 2026-09-03 | Phase 1 T1.3 assumed a schema that does not exist | T1.3 told the implementer to "find the schema that validates `moc-structure-cache.yaml` entries" and register the new field there. Direct inspection during implementation found no such schema: `tomo/schemas/` has no `moc-structure-cache.schema.json`, no file there mentions `up_state` at all, and `tomo/scripts/lib/moc_cache_loader.py` reads the cache with a bare `yaml.safe_load` — no schema validation of any kind, only staleness checks. CON-6 ("schema and its mirror stay bytewise identical") never applied; there was no mirrored schema to keep identical, because there was no schema. **Decided:** T1.3's success criterion — the absence semantics stated so the next reader does not have to infer them from the sentinel — is met by documenting `up_broken_reason` in `docs/tomo/scripts/moc-tree-builder.md` instead, per the root CLAUDE.md rule that runtime rationale belongs in the WHY-persistence layer. Creating a JSON schema for this cache was considered and rejected as out of scope for this spec. `plan/phase-1.md` T1.3/T1.4 corrected to match. |
| 2026-09-03 | Phase 3's Registration inventory undercounted by three sites | The SDD's Registration inventory — the operative list `plan/phase-3.md` builds T3.1/T3.2 from — listed six must-register sites and three must-not-register sites. All nine were real and correctly cited, but the list was incomplete: three more sites live in `garden-audit-stats.py`, a stats-view surface that duplicates check-name knowledge instead of reading it from the checks that own it. The most severe: `garden-audit-stats.py:49-51` runs `assert set(_CHECKS) == set(ALL_CHECK_NAMES)` at **module scope** — registering `parent_not_moc` in `ALL_CHECK_NAMES` without widening `_CHECKS` here makes the stats module raise `AssertionError` **on import**, before any test runs, taking down `/garden-audit stats` entirely. `_COL_LABEL` (`:63-66`, indexed unconditionally at `:119`) and a third, independent check-name enum in `garden-audit-exclusions.schema.json:73` (validated by the configure wizard before it writes an exclusion) were the other two. A fourth site, a stats-local `_TIER` table, is a should-register consistency fix, not a hard break — it is shadowed by the finding's own `tier` field at read time. **Decided:** correct the inventory to nine must-register + one should-register + three must-not-register (thirteen total), correct the prose-description count from two to four (the two sentences are duplicated verbatim across `doc.schema.json` and `wire.schema.json`), and strengthen T3.2 so it proves the inventory's own completeness (an independent grep classifying every occurrence of an existing check name) rather than only walking the table that had already been proven incomplete once. `solution.md` and `plan/phase-3.md`/`plan/README.md` corrected to match. |
| 2026-09-03 | ADR-4's reappearance case is real on this vault, not hypothetical (T3.3) | Ran the actual `GardenExclusions` loader (`lib/garden_exclusions.py`) against the live instance config, `tomo-instance/config/garden-audit-exclusions.yaml` (six rules). **4 of 6 auto-cover**: `Calendar/`, `X/`, `100 Inbox/`, and `Atlas/` all use `checks: all`, which expands over `ALL_CHECK_NAMES` and picked up `parent_not_moc` with zero config edits — confirmed by probe (`is_excluded(Calendar/…, "parent_not_moc") == True`). **1 of 6 will see reappearance**: `Efforts/` names checks explicitly as `[broken_up, dead_link, stale_moc]`; the same probe shows `is_excluded(Efforts/…, "broken_up") == True` but `is_excluded(Efforts/…, "parent_not_moc") == False` on the identical note — any `broken_up` finding under `Efforts/` that reclassifies as `parent_not_moc` after this spec ships was silenced before and is **not** silenced after. The sixth rule, `(root)` → `[stale_moc]`, never named `broken_up` in the first place, so nothing there changes. **Decided:** this is not a migration bug to fix — ADR-4 already calls the reappearance defensible (a different statement about a different note) — but it is a real, user-visible change on the vault this spec was measured against, so it goes in `docs/XDD/backlog.md` as a release note rather than being left for the user to report as a regression. |
| 2026-09-04 | Sites 12 and 13 have no independent behavioural defence — found by the T3.2 addition walk, not by review | T3.2's addition walk (must-not-register sites) adds `parent_not_moc` to each of the three deliberately-omitted sites and expects a test to fail. Site 11 (`garden-audit.py`'s `_FIXABLE`) failed loudly as expected. Sites 12 (`garden-audit-render.py:575`, the suggest-targets tuple) and 13 (`:814`, the enrichment tuple) did not — adding the name to either, in isolation, left the full `test_garden_audit_render.py` suite (143 tests) 100% green. Traced, not guessed: both tuples sit inside code reached only via `elif decision is not None:` (`:527`), and `decision` is attached to a wire finding only when `build_wire_payload` (`:926`) sees the doc-level finding is fixable — which `_FIXABLE` (site 11) controls exclusively. `parent_not_moc` is never in `_FIXABLE`, so no `decision` block is ever built for it, so neither branch is ever reached; site 13's own `_enrich_block` (`:765`) adds a second, independent guard (no ticked-checkbox line in an advisory block, ever). **These two sites are structurally transitive on site 11, not independently defended.** No behavioural test can cover them, because there is no behaviour to observe. **Decided:** assert the tuples' literal contents directly instead — two `ast`-based tests in `tests/test_garden_audit_registration.py` that parse the real source (not a text search) and fail the moment either name is added, regardless of whether the resulting code stays reachable; the realistic regression this guards against is an editor tidying up and adding `parent_not_moc` to a check-name list "for consistency," not a behaviour change. Proven RED before shipping: both tests were run against a scratch-mutated copy of `garden-audit-render.py` with the name added to each tuple, confirmed to fail, then restored (`git status` clean throughout — no edit to `garden-audit-render.py` itself). CON-2's real defence for the fixable/advisory split is now stated plainly: `_FIXABLE` (tested, loud) plus `garden-audit-parser.py`'s literal `check == "broken_up"` gate (`:403`/`:603`, tested, independent) — two genuine layers; sites 12/13 are downstream of the first, not a third. |
| 2026-09-04 | The advisory's shared-target wording is a grouped block, not repetition (user decision) | The TDD gate refused T4.1 twice, correctly: the SDD delegates the exact strings to the implementer, so no test could be written against a string that did not exist. Three options were drafted and the grouped form chosen — a light per-finding line plus one once-per-run **Untagged parents** block listing each shared target with its finding count. It is the only option satisfying the PRD's own Should-Have (*presented together rather than repeated*); the per-finding-sibling variant **is** the repetition that criterion warns against. Measured stakes: 7 of 20 advisory findings point at just 3 parent notes, so the block names the three highest-leverage actions in one place. The gate's second pass then found three untested corners — block suppression when nothing is shared, the group-size-1 line, and the finding-ID source — plus a plural bug ("resolves all 2") that only T4.5's prose read would otherwise have caught. All four are now written into the task. |
