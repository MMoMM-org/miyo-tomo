- **Docs-only / analytical tasks still need a spec-compliance pass focused on CITATION INTEGRITY — it's the docs-task equivalent of running the test suite.** When a task's deliverable is prose carrying `file:line` / ADR / spec citations rather than code, run a reviewer that OPENS each cited location and confirms it actually supports the claim, and confirms no figure is presented as a measurement unless it's quoted from a real file. F-41 T6.2/T6.3 (2026-06-11): the `cost-analysis.md` doc cited a bare `README.md:55`, which resolves to the **repo-root** README (an architecture table) instead of the spec-level `docs/XDD/specs/016-.../README.md:55` where the `~$26/run` figure lives — an ambiguous citation that reads as correct until someone follows it to the wrong file. The same pass confirmed zero fabricated cost numbers (every projected figure was explicitly labelled "analytical bound"). Rules: (a) an unqualified `README.md:NN` is a hallucination trap in any repo with nested READMEs — always qualify the relative path; (b) when a measured number can't be produced (e.g. live cost run blocked by Kado 429 from host), document the analytical bound + a deferred in-container validation step rather than inventing a figure.

- **When documenting a filename pattern or any code-generated format, READ THE GENERATOR FIRST.** Don't guess from doc-text, from a sibling doc, or from memory. F-55 sweep: my initial fix to `instruction-builder.md` used `tomo-moc-proposal-<YYYYMMDD>-<HHmm>-<slug>.md` — copied from `moc-architect.md` — when the actual producer (`suggestions-reducer.py:558-561`) was both the source of truth AND the outlier (it produced a format inconsistent with the canonical Tomo `<YYYY-MM-DD>_<HHMM>_<role>.md` shape used by suggestions/instructions/suggestions-fan). The 1-line doc-text fix turned into a 7-commit producer + consumer + doc + test sweep once the generator was actually read. Path: `grep -n 'filename = ' producer.py` → read `strftime` format → that IS the answer. Applies to filenames, frontmatter blocks, JSON payload shapes, anything Tomo emits programmatically. **Bonus principle**: when fixing a documented format, also verify producer + consumer + sibling docs all agree before committing the doc fix in isolation — silent drift between them is the trap.

Examples: `2026-05-22_1407_suggestions.md`, `2026-05-22_1407_instructions.md`, `2026-05-22_1407_suggestions-fan.md`, `2026-05-22_1407_moc-proposal-zsh-shell-tools.md`. Backward-compat: parser + mark-captured filter accept the legacy `tomo-moc-proposal-*` pattern so pre-F-55 vault files don't orphan. F-55 shipped 2026-05-22.

- **Spec/schema contradiction → deviation note pattern.** When a task spec asks for output that violates a downstream schema, document the deviation in the plan file under that task with: (a) the schema constraint that blocks literal compliance, (b) the consumer behaviour that makes the deviation safe, (c) the chosen alternative. Don't quietly comply (downstream breaks); don't push back blindly (spec author had a reason). F-43 T4.3 example: spec said "stub `result.json` with `actions: []`" but `item-result.schema.json:33` declares `actions:{minItems:1}`; pragmatic fix was to skip writing `result.json` entirely and rely on `suggestions-reducer.py:758` "skip gracefully" handling. Recorded as a deviation block in `phase-4.md` under T4.3.
- **Module-level imports execute regardless of textual position — late imports are not bugs.** Pytest collects all module-level statements before invoking any test function; function bodies resolve names at call time. A `from lib import foo` at line 268 (after test functions calling `foo.bar()`) is a code smell, not a NameError. When a code-quality reviewer flags "Critical NameError" on test code that demonstrably passes, **run the tests first** before applying the "fix". Hoist for hygiene if you wish, but don't treat this class of finding as a blocker.
- **Mock shape must match the consumer's actual access pattern, not your intuition.** Augments `feedback_mocks_verify_library_reality.md` (auto-memory): the rule applies even when YOU are authoring the mock for in-house code in this same session. Read the consumer's accessor expression (`note["content"]` vs `note.content` vs `note.get("content")`) before finalising the mock's return shape. F-43 T4.4 e2e: my fake `read_note` returned a class with `.content`; renderer at `instruction-render.py:405` used `note.get("content", "") if isinstance(note, dict)`; tests silently fed empty content and Rule 4.2/4.5 paths emitted wrong action counts.
- **Deferred-pipeline-assembly creates "half-wiring" deviations — surface, don't expand scope.** When a child task assumes a parent pipeline is wired but the parent shipped helpers individually without an orchestrator (`main()` raises NotImplementedError), the child task may correctly ship its half (e.g., load+save) but not the threading. Pattern: document as a deviation in the plan file naming the missing parent task; don't grow the child's scope to fix the parent gap. F-43 T5.1 example: `phase6_dedupe(squelch_registry)` call site doesn't exist because Phase 2 left `main()` un-assembled; T5.1 shipped load/decrement/save and noted the threading deviation under its task entry in `phase-5.md`.

F-43 (MOC-creation skill) had ~70% of the spec already in place — `tier-3/lyt-moc/new-moc-proposal.md`, `moc-matching.md`, `t_moc_tomo` template, and the `create_moc` / `add_relationship` actions in `instructions.schema.json` — that a greenfield brainstorm would have duplicated. - **Tomo runtime scripts must use instance-correct, cwd-relative path DEFAULTS — not `SCRIPT_DIR.parent.parent`-based ones.** The instance layout is flattened (`tomo-instance/{scripts,config,schemas}`) while the repo nests under `tomo/`; a `SCRIPT_DIR.parent.parent/config/...` default resolves to `tomo/config` on the host (exists) but to a non-existent `<repo>/config` in the container — so the registry/groups dirs silently loaded empty and tag-handler routing was disabled (spec 024, Pass-1 **and** Pass-2). Rule: default paths cwd-relative (`config/tag-handlers`, `tomo-tmp/...`) so omission is *safe, not fatal*; runtime commands call bare `scripts/foo.py` with NO path switches; switches exist only for host/test overrides. Give a new pipeline script instance-cwd defaults from the start, and verify the CONTAINER invocation (grep the command file) — not just a host run that passes the flag.

<!-- 2026-07-20 -->
- **Unit tests with clean/synthetic fixtures mask live-dirty production data — add at least one test built from a REAL sample of the actual data store.** garden-audit (spec 030): render + parser tests used clean `up_target` values (a real list or a clean str), all green, but the live `moc-structure-cache.yaml` stored `up_target` as a *stringified* Python list-repr `"['020 Active MOC']"` (type `str`) for 32/339 notes — a shape no fixture exercised — so the `[[['020 Active MOC']]]` render leak shipped and was caught only by the user reading a live report. Root cause was upstream (`up_parse._first_wikilink` treating a list-repr string as a bare stem, which also *falsely* flagged those notes `broken_up`). Rule: when a script consumes a cache/vault/DB artifact, dump a real sample (or reproduce the exact dirty shapes observed) into a fixture — hand-authored clean data proves nothing about the messy reality. Sibling of the `feedback_validate_against_live_sample_not_spec` + `feedback_fixture_from_live_render` auto-memories.
- **Test the CLI entry point through `main()`, not just the helper functions it calls.** garden-audit-parser: `build_from_report` / `build_from_wire` were unit-tested green, but `main()`'s dispatch — route edited-wire→`build_from_wire` vs unedited→`build_from_report`, and degrade to empty output on a missing/unreadable `--wire` — was never invoked by any test, so a mis-wired CLI (or a crash on missing wire that would break *every* apply) could ship. The spec-compliance reviewer caught it, not the suite. Fix: tests that patch `sys.argv` + capture stdout via `capsys` and call `main()` directly. Rule: for any script the pipeline invokes as `python foo.py --flags > out.json`, at least one test must exercise `main()`/argparse routing (incl. the graceful-degrade branch), not only the callees. Extends the `feedback_mock_at_orchestrator_not_helper` auto-memory to the CLI boundary.
- **Fuzzy-similarity ratios (`difflib.SequenceMatcher`) are inflated by shared boilerplate — gate EVERY match signal with a cutoff, and test the pure-noise case.** garden-audit Phase 7 `suggest_repoint_mocs`: every MOC stem carries the ` MOC` suffix, so `difflib.ratio("Writing MOC", "Cooking MOC") ≈ 0.64` — two semantically unrelated MOCs scored "similar" purely on the shared suffix. With no cutoff on the stem-similarity signal, a note with no topic overlap got three confident-looking-but-wrong repoint candidates. Fix: a `stem_cutoff=0.6` gate (a real typo `Writng MOC`→`Writing MOC` still scores 0.95, so legit matches survive). Rule: any fuzzy/similarity signal feeding user-facing suggestions needs (a) an explicit cutoff calibrated against the shared-boilerplate floor, and (b) a test that feeds pure noise (a target with no real affinity beyond the boilerplate) and asserts an EMPTY result — that test is what catches suffix/prefix inflation. Also: when merging two similarity signals (topic-overlap vs stem-distance), they're different scales — don't sum; take max, and gate each independently.
- **Producer/consumer paired-filename contracts: the producer's name MUST match the consumer's derivation rule, and a test must lock producer-name == consumer-derivation.** garden-audit (spec 030): the report was published as `garden-audit-<epoch>.md` and the wire as `garden-audit-wire-<epoch>.json`, but the consumer `inbox-triage._cache_wire_sibling` derives the wire from the report by a FIXED rule — `report_path[:-3] + ".json"` (the `.md`→`.json` sibling). The `-wire-` infix meant the derived name (`garden-audit-<epoch>.json`) never matched the actual wire, so the wire (the parser's REQUIRED structure source) was never found → empty confirmed_items → the entire apply path silently no-op'd, with NO error. Fixing the producer to the canonical inbox convention (`<YYYY-MM-DD_HHMM>_garden-audit.md` + its `.json` sibling) resolved it AND fixed `_get_doc_type`'s `stem.endswith("_garden-audit")` filename fallback. Rule: when a producer writes a file whose paired artifact a consumer locates by string derivation (sibling `.json`, `_role` suffix, timestamp prefix), (a) make the producer follow the SAME convention the consumer already assumes, and (b) add a test that computes the consumer's derivation from the producer's name and asserts equality — a mismatch here fails silently, never loudly. Sibling of the two-artifact/wire-parity learnings.

<!-- 2026-09-04 -->
- **Read the rendered output as prose — it finds a class of defect no test can reach.** Spec 033 T4.5 rendered a report containing every finding combination and read it end to end as English. That found **five** defects a 3003-test suite and two independent review gates had all passed: the Summary filed a finding under a cause its own block explicitly disclaimed ("Flagged parents: 9 — 3 not found in the audited area" counting a finding whose block said *Tomo cannot tell*); a clause claimed the split line answered *why* when it answers *where*; a heading asserted "Broken" above a body saying the cause was unknown; the same assertion again in the detail line after the heading was fixed; and a stray blank line in every advisory block. None was findable by a test, because no test reads. Spec 032 had already written the lesson down after shipping a block whose heading said `up::` while its fix line said `up` property — green tests, both gates passed, caught by the first person to read the output. Rule: for any script whose deliverable is **text a human reads**, add a task that renders every combination and reads it; and structure it so an agent renders while a human (or the orchestrator) reads — an agent reporting "I read it and it's fine" reproduces the exact failure, a green signal from something never examined.
- **A test that encodes observed output rather than asserted behaviour becomes complicit with the bug.** Spec 033 found `_SPLIT_LINE = "Broken parents: {total} findings — ..."` used with `total=1` at four call sites, all passing — *because* `garden-audit-render.py` hardcoded the same wrong plural. The test and the defect agreed with each other, so the suite locked "1 findings" in place instead of catching it, and fixing the code broke the tests. Sibling rule from the same spec: **any `f"{n} <noun>"` needs an explicit `n == 1` test.** Three instances shipped or nearly shipped in one spec — `resolves all 2`, `1 findings`, `1 targets` — each surviving because no fixture ever had exactly one. A fixture of three never exercises the singular. When writing an assertion, ask whether it states what the output *should* be or merely what it *currently is*; only the first can fail usefully.
- **A claim asserted in several places within one block is a multi-pass defect — enumerate every site before fixing any.** Spec 033's cause-unknown finding said "Unclassified parent link" in its heading and "Broken `up::`" in the line directly beneath it; fixing the heading moved the contradiction down one line rather than resolving it. Spec 032 hit the identical shape one release earlier and needed **three** commits (0.18.0 → 0.18.1 → 0.18.2) to kill it; 033 needed two. Fixing sites one at a time as each is spotted by reading is a losing game. Rule: when a contradiction is found in rendered text, grep the module for **every** place that makes the same claim — heading, detail line, fix summary, withheld block, summary lines — and confirm the corrected path is consistent in all of them before calling it fixed.
- **Code that is structurally unreachable needs a structural assertion, not a behavioural test.** Spec 033's `parent_not_moc` must never appear in `garden-audit-render.py`'s suggest-targets or enrichment tuples. Adding it to either produced **zero** test failures across the full 143-test render suite — both sit behind `decision is not None`, and `decision` is attached only when `_FIXABLE` says fixable, which correctly excludes the check. The sites were defended transitively, not independently. Fix: `ast.parse` the source, locate the tuple literals by content (not line number), and assert the name is absent — plus `assert tuples` so a rename or restructure fails loudly instead of silently matching zero. Rule: when a guard's code path cannot execute for the input you are guarding against, a behavioural test proves nothing; assert the literal, and make the test's docstring say why, or the next reader deletes it as a pointless string check.

<!-- 2026-09-11 -->
- **A sweep that removes a pattern from producers does not remove it from consumers — and a guard scoped to producers will report the job done.** Spec 035's ADR-5/T3.1 removed every `schema_version` literal from the three renderers and added `test_no_renderer_hardcodes_schema_version`, which scans **renderer** source for a reintroduced literal. It passed. Three *acceptors* went on comparing `wire.get("schema_version")` against the bare literal `"1"` — `suggestion-parser.load_changed_wire`, `inbox-triage._load_edited_wire`, `garden-audit-parser._is_wire_edited`/`load_changed_wire` — and were found **one at a time, by tripping over them**, across two later tasks. Each would have failed silently: on a version bump they return "not authoritative" with no error, so every user edit to a wire document is dropped and the pipeline falls back to markdown as if nothing happened. The guard's scope became the sweep's perceived scope. Rule: when removing a pattern, grep for the pattern's **complement** — every producer implies a consumer, every emitter an acceptor, every writer a reader — and either extend the guard to both sides or state in its docstring which side it does not cover. A repo-wide grep at the end confirmed the class was finally closed (the one remaining literal governs a non-published schema); that grep should have been the first step, not the fourth.
- **A diagnostic message is the single most likely place for sensitive content to escape a privacy-first system, and a good-faith improvement is how it gets there.** Spec 035 T4.2b: I required a render-path failure to raise loudly rather than silently emit an invalid document, and specified that the message "name the entry's discriminating value" — without checking what that field *is* per bucket. `_DAILY_DISCRIMINATOR` maps `log_entries` → `content`, so the raise quoted a user's daily-note text verbatim into a `ValueError`. The MiYo Constitution (L2) forbids exactly this: operation traces record metadata only. Worse, the test added alongside asserted the message **contains** the discriminator value, so it encoded the violation and would have preserved it. Fixed by mapping each bucket to a permitted locator (`field`, `source_stem`, `target_stem` — all metadata or path-like), and by two guards rather than one: a `not in message` assertion in the parametrized test plus a separate non-parametrized test that cannot be dropped by editing the parametrize list, with a deliberately sensitive fixture string so the guard has something real to catch. Rule: any message built from user data needs the field's *identity* checked, not its role — "the discriminating value" and "the note's text" can be the same field. Diagnostics are written for failure paths, which is exactly where they reach logs, tracebacks and pasted bug reports.
- **A runtime change that improves a mechanism leaves behind the document explaining the mechanism it improved away — tests go red, docs do not.** Four instances in one session of `docs/tomo/<path>.md` contradicting the runtime file it mirrors, and **two of them argued against the shipped code**: `suggestion-parser.md` stated that putting `source_item_key` on the wire "is not available" and that a positional join "would silently rebind keys to the wrong notes" — both describing exactly what the new code does. In this repo the WHY layer exists to stop a future reader "fixing" a deliberate decision; a doc in that state actively recommends the regression. The fix that worked was **splitting rather than overwriting**: the old warning stayed, correctly scoped to the mechanism it describes (the markdown path, where a human may edit between render and re-parse), and a new section explained why the wire path is safe *despite* it (both lists derive from one `json.load` inside one call — no human-edit boundary). Rule: when a change makes a doc's claim false, ask whether the claim was false or merely **narrower than it looked**; deleting a correct warning because the code now contradicts it is the same move as editing a test to match an implementation.

- **Run a finished detector over real data before declaring it correct — a green suite says nothing about a mechanism nobody has pointed at reality.** Spec 035 built a wire-shape detector, shipped it through Phases 1-3 with ~3900 green tests and two independent review gates per task, then vendored the consumer's actual schemas in Phase 4 and ran the detector across them. That single run exposed **two defects in the classifier and one live drift the spec's own research had missed**: (a) a false positive — a newly-added property carrying an enum emitted one `added_enum_value` per value, each classified consumer-affecting, though the consumer does not declare that property at all, so no enum of theirs can be violated (live over-report ratio 4:1); (b) a false negative, the dangerous direction — `removed_enum_value` conflated "a value left an enum that still exists" (safe narrowing) with "the enum constraint vanished entirely" (we may now emit anything while the consumer still enumerates and rejects), so replacing a closed enum with a free string produced silence and the gate passed; (c) `parent_not_moc`, a live consumer-affecting drift from commit `2111772` — **the very commit the spec's decision log already cited** for two other fields. The research read `findings[].detail` and stopped, finding two of that commit's three wire changes. Rule: a detector is unproven until it has run against the real artefact it was built to watch. Tests exercise the cases you imagined; the artefact contains the ones you did not.
- **`git grep` searches tracked files only — a test that shells out to it passes while its own subject is untracked, then fails the moment it is committed.** Spec 035 T3.2 added a tripwire asserting nothing binds a canonical `$id` URL to the producer schema. It ran `git grep` for the URL, filtered known-good hits, and went green in the full suite. It was green because the test file itself was still untracked at that moment; once committed, `git grep` saw the file's own `CANONICAL_ID = "..."` constant and its docstring, and the test found *itself*. The implementer's suite result was honestly reported and still wrong — green as an artefact of *when* it ran. Rule: any test that invokes `git grep`/`git ls-files` must be run after `git add` of its own file, never before; and its exclusions must cover the test's own path (`Path(__file__).relative_to(REPO_ROOT)`, so a rename keeps it correct). Related trap in the same test: `git grep` exits **1** for "no matches" and ≥2 for a real error — code treating any non-zero as "nothing found" makes the tripwire pass silently when the search itself failed.
- **A fixture name is not a contract — two test files can define the same fixture name over different files and never collide.** `tests/test_instruction_render_wire_hygiene.py` and `tests/test_wire_snapshot_parity.py` both define `instructions_schema` loading `instructions.schema.json`; `tests/test_edit_note_text_action.py:38` defines `instructions_schema` loading **`hashi-instructions.schema.json`** — a different document (the Hashi mirror, which carries a `replace_section` def the producer copy lacks). pytest resolves fixtures per-module, so nothing breaks today. The trap is the unification: anyone promoting `instructions_schema` to `conftest.py` to remove the duplication would silently bind one of those three call sites to the wrong schema, and the suite would stay green because both documents are structurally near-identical. Rule: before hoisting a duplicated fixture into a conftest, grep the repo for the **name** and confirm every definition loads the same source — same-name/different-source is the case that survives the refactor and fails later.
