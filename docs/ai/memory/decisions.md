<!-- 2026-06-12 -->
- 2026-06-12 — Decision: Keep the F-41 `inbox-analyst` on **Sonnet** with the v0.17.0 de-biased two-pass Step 7.5 prompt as the segmentation floor; reverted two tuning experiments — the mandatory `topics_enumerated[]` forcing field (was v0.18.0) and an **Opus 4.8** analyst (was v0.19.0). — Rationale: Neither improved segmentation. **Enumeration ≠ emission** — the model dutifully lists N topics but still emits the same atomics. The apparent "under-segmentation" was largely a **measurement artifact**: the un-emitted enumerated topics were appointments/errands that correctly route to the daily-log (`log_entry`/`log_link`), NOT dropped atomics — so a voice memo enumerating N topics legitimately yields 1 atomic. Opus cost **+57%** (20-item Pass-1 ~$22.6 vs ~$14.4 Sonnet, 1.67×/token) for the same correct evergreen-vs-appointment discrimination. Dead-end commits preserved on branch `backup/f41-forcing-field-experiment`; full WHY in `docs/tomo/dot_claude/agents/inbox-analyst.md` v0.17.0 mirror. Lesson: before "fixing" under-segmentation, confirm the missing items are actually atomic-worthy and not correctly routed elsewhere.

<!-- 2026-06-06 -->
- 2026-06-06 — Decision: `/moc-propose` whole-vault `scan` selects candidates by **orphan state** (`up_state==absent`) sourced from the moc-structure-cache (no live `list_dir`); scoped runs (`folder:`/`tag:`/`class:`/`title:`) still consider ALL in-scope notes; `candidate_cap` default 200→500. — Rationale: the old cap counted every atomic note incl. already-MOC-linked ones, so it measured vault size, not "notes needing a MOC" — any mature vault tripped `candidate-cap-exceeded` (live: 209>200), defeating 021's whole-vault-discovery goal. The cache already carries `kind==note` entries with `up_state`+`topics`, so orphan-sourcing avoids both the live pull AND LLM topic extraction (Phase-2 topic-index extended over note entries). Folded into 021 as Feature 6 / ADR-11. Design smell to watch: a cap on input size instead of on "items that need action" — filter by the state that defines the work.

<!-- 2026-05-26 -->
- 2026-05-26 — Decision: Voice transcription routing lives in `/inbox` command, NOT in conductors. When `inbox-triage.py` determines `action=transcribe`, `/inbox` dispatches `voice-transcriber` directly and exits — conductors never run. The suggestion-conductor v0.1.0 had a full voice section (Steps 2, precheck, dispatch, stop-gate) that was dead code since the /inbox command already handled it. Removed in v0.2.0. — Rationale: Transcription is a stop-gate (creates files, then user must review before re-running). Handling it at the /inbox level means the conductor never instantiates, saving all common-setup overhead. Surfaced during 018 code review 2026-05-26.

<!-- 2026-05-20 -->
- 2026-05-20 — Decision: Tomo's vault-write pattern is **"scripts produce locally, agents transport via Kado"**. Python scripts (`suggestions-reducer.py`, `suggestions-render.py`) write rendered artefacts to `tomo-tmp/` on the local container filesystem; the orchestrating agent (`inbox-orchestrator`, `moc-architect`) then `Read`s the file and invokes `mcp__kado__kado-write` to push it into the vault. Scripts have NO Kado-write dependency. — Rationale: Keeps script unit-testable without a Kado fixture; centralises the Kado interaction in agent specs where the inbox-path resolution + transport audit lives; matches the established `inbox-orchestrator` Step C4 contract. When authoring a new agent that produces vault output, mirror this split — do NOT pass a vault inbox path as a script's `--output-dir`, because the script will write to the container's local fs (path lookalike, no vault visibility). Surfaced as a real bug in F-43 T6.5.5 live validation: `moc-architect` Step 7 passed `100 Inbox/` as `--output-dir`, file landed in container fs, user couldn't find it. Counter-example: `instruction-render.py` writes via Kado from inside the script — accepted because Pass-2 writes touch many vault paths (one Kado call per child note + per MOC), batching at agent level would explode the agent's tool-call count. **One-shot final transport → agent. Many small writes → script with embedded Kado client.**

<!-- 2026-05-06 -->
- 2026-05-06 — Decision: External Obsidian skill/agent collections (e.g. `obsidian-ops-team` from davila7/claude-code-templates, `obsidian-bases`/`obsidian-markdown`/`json-canvas` from aitmpl.com) must pass a **Kado-MCP-compatibility check** before being absorbed into Tomo. — Rationale: Tomo's L1 invariant (CLAUDE.md root rule) is "NEVER modify vault files directly — all vault access goes through Kado MCP". Many community Obsidian skills hardcode direct filesystem access (`Read`, `Write`, `Bash` on vault paths, e.g. `/Users/cam/VAULT01/...` in obsidian-ops-team) which violates this contract. Outcome: direct-FS sources are **inspiration-only** (decomposition map, agent-shape patterns), not importable. Reference-style skills (markdown syntax, base spec, JSON canvas spec) without behavioural code can be absorbed as `tomo/skills/<name>/` (`user-invocable: false`, lazy-loaded), since they don't invoke filesystem at runtime. Documented during F-43 source evaluation 2026-05-06; see `docs/XDD/roadmap-obsidian-power.md` "Reference-skill absorption" table.
